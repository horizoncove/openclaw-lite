# 致 MiniMax：技术方案与功能修改意见

> 发文方：西安微短剧产业服务 SaaS · 文档/审核线  
> 对象：https://8jatajrnp6c9b.space.mcode.cn/#demo（v1.0 · 2026-07-24）  
> 依据：我方已拍板 PRD/ARCHITECTURE **V1.2**（会员协作中枢 + API 聚合 + 算力调度；**不做 Token 转售**）  
> 目的：在保留你们「撮合交易演示包装」优势的前提下，对齐真实可交付产品，避免理事会材料与工程现实脱节。

---

## 0. 总评（先读）

你们的演示中心在 **叙事完整度、撮合品类颗粒度、对外一页入口** 上完成度高，适合理事会「看得见」。

但当前方案存在三类硬伤，建议优先改：

1. **产品主轴过窄**：整站以「出海撮合」为唯一主路径，弱化了会员日常经营（项目、进度、通知、统一 API/算力）。  
2. **Token 设计与业务决策冲突**：高保真仍含 Token 页；若走向转售/挂单，与联盟侧已确认「只做官方充值消耗、不做转售」不一致。  
3. **技术口径超售**：可用版实为 `localStorage` 前端原型，却与「6 层 / 多区域 / 等保三级」并陈，易被技术 Lead 一次问穿。

**修改原则：** 把出海撮合降为「专业服务线」；把会员中枢 + 官方钱包网关 + 算力作业升为「主路径」；把目标架构与已交付能力分栏书写。

## 1. 产品定位修改意见

### 1.1 一句话定位（建议替换）

| 现状（你们） | 建议改为 |
|--------------|----------|
| 陕西微短剧**出海** SaaS 平台 | 微短剧**产业会员协作中枢**（含出海等专业服务） |

建议首页 Hero 能力顺序改为：

1. 我的项目与进度  
2. 全联盟工作需求（发布/应征/成交）  
3. **API 聚合网关 + 算力作业**（统一 Key、计量）  
4. 撮合机会与联盟通知  
5. 出海/译制等专业服务（二级入口）

### 1.2 KPI 面板修改

| 建议保留 | 建议调整或降权 | 建议新增 |
|----------|----------------|----------|
| 语区覆盖、海外平台数 | 「撮合品类 5」改为「需求品类 + 服务线」 | 机构钱包调用量、作业成功率、需求成交率 |
| 会员数 30+ | 勿把「等保/多区域」当 MVP 指标 | API 可用模型数、日调用量（演示也可用模拟） |

### 1.3 明确「不做」清单（必须写入方案正文）

请在技术方案与高保真中增加红线页：

- ❌ Token / 额度 **转售、挂单、机构间转让**  
- ❌ C 端播放与硬币充值  
- ❌ 把「算力」做成可倒卖的额度商品（算力应是 **作业调度 + 计量**，不是二手盘）

高保真里的 **「Token」页请删除或改名为「机构钱包 / API 用量」**，仅展示：官方套餐购买、余额、流水、API Key。

## 2. 功能修改意见（按模块）

### 2.1 可用版 IA：从「16 页出海站」改为「会员主路径 + 撮合增强」

**建议导航（会员端）**

| 导航 | 优先级 | 说明 |
|------|--------|------|
| 工作台 | P0 | 待办、逾期、阻塞、未读通知、开放需求、进行中作业 |
| 我的项目 | P0 | 阶段、任务、阻塞；可关联需求与算力作业 |
| 工作需求 | P0 | 全联盟广场 / 我发布的 / **我应征的**；状态机见下 |
| 撮合机会 | P0 | 保留你们路演位/试点名额类机会；与「需求广场」区分 |
| API 与算力 | P0 | Key、模型目录、试调用、用量流水、**作业队列** |
| 消息中心 | P0 | 公告 + 已读回执 |
| 机构设置 | P1 | 资料、成员 |
| 出海服务台 | P1 | 译制/发行等工作台作为专业服务入口，不占首页主叙事 |

**你们现有优势请保留并挂接：**

- 5 品类（译者/配音/IP/发行商/算力）→ 映射为 `demand.category` 枚举  
- 撮合大厅 / 订单 / 供应商市场 → 作为「需求成交后的履约层」，不要替代「项目与工作台」

### 2.2 需求状态机（请统一文案与 UI）

```
草稿 → 已发布(全联盟可见) → 对接中 → 已成交 / 已关闭
```

修改点：

- 已发布后 **不可** 改回「仅私下可见」；下架用「关闭」  
- 应征方不能应征本机构需求  
- 确认成交后：生成 **订单/履约单**（保留你们担保交易叙事）+ 可选生成项目任务  
- 广场需支持：品类 / 语区 / 紧急度筛选（你们有品类，请补语区与状态筛选）

### 2.3 「算力」功能重做（关键）

| 现状倾向 | 建议形态 |
|----------|----------|
| 算力作为撮合市场上的供给方卡片 | **算力作业（Job）**：提交 → 排队 → 运行 → 成功/失败 |
| 像买额度商品 | 与机构钱包同一账本：预扣 / 成功实扣 / 失败释放 |
| 无项目归属 | 强制或默认绑定 `project_id` |

最小页面：

1. 提交作业（类型：字幕批处理 / 配音 / 图生视频…、优先级、输入说明）  
2. 队列列表（状态机可视化）  
3. 完成后回写项目进度或发通知  

「算力供应商」可保留在供应商市场，但成交后应进入 **作业/工单**，而不是停留在「挂单买卖」。

### 2.4 API 聚合（你们技术方案需补的能力，演示也要有入口）

请在可用版增加真实可感知的「网关」页（即使第一期仍是 mock）：

- 机构级 API Key（展示一次 + 轮换）  
- `POST /v1/chat/completions` OpenAI 兼容说明  
- 模型目录与标价  
- 试调用后 **余额下降 + 流水可查**  
- 余额不足返回明确错误（402），且说明「不执行上游」

这是与纯 localStorage 撮合站的核心差异化，建议在演示中心首页用一句话标出：  
**「统一模型网关 + 机构钱包计量（非 Token 转售）」**。

### 2.5 联盟担保交易（建议保留并收束）

保留：需求 → 匹配 → 签约 → 订单。  
修改：

- 「担保」要写清规则：谁托管、何时放款、争议谁裁（秘书处），避免只有按钮没有规则  
- 订单必须关联：需求 ID、甲乙机构、金额/节点、状态  
- 与钱包关系：服务费/担保费可走官方账户；**禁止**出现余额转让给其他机构的入口  

### 2.6 通知与秘书处

补齐：定向（全体 / 层级 / 标签）、已读回执、跳转到需求或订单。  
秘书处侧：撮合标注、机会运营、通知发布——不要只做会员端。

## 3. 技术方案修改意见

### 3.1 必须拆成「两栏」：已交付 vs 目标架构

| 栏目 | 允许写什么 | 禁止写什么 |
|------|------------|------------|
| **当前演示** | localStorage / 静态原型 / 模拟数据 | 等保三级已具备、多区域已部署 |
| **目标架构（Phase 2+）** | 6 层、多 AZ、陕+新+德、GDPR、等保路径 | 写成「平台已具备」 |

建议在技术方案扉页加醒目声明：

> 本演示中心「可用版」为前端可交互原型（localStorage）。等保、多区域、高可用属建设目标，不在本演示验收范围。

### 3.2 推荐逻辑架构（请替换或并列到你们的 6 层图）

```
Member Web
    ├── Platform API（项目/需求/通知/订单/RBAC）
    ├── XD-Router（OpenAI 兼容同步推理 + 计量）
    └── Compute Scheduler（异步算力作业队列）
              ↓
     PostgreSQL · Redis（限流）· Object Storage
```

说明：

- 「AI 层」不要悬空：应落为 **Router Adapter + Job Worker**  
- 「API 网关」区分：边缘网关（鉴权/限流）≠ 业务上的 **模型聚合网关**  
- 出海译制工作台通过 `service_requests` 挂项目，而不是另一套孤岛系统  

### 3.3 数据模型必改清单

**删除 / 禁止：**

- `token_resale_*`、余额转让、挂单撮合表  

**必须具备：**

```
orgs, users, projects, tasks
demands, demand_applications, match_orders      -- 保留你们订单能力
wallets, token_packages, token_orders, token_ledger
llm_providers, llm_models, api_keys(key_hash), usage_records
compute_pools, compute_jobs, compute_job_events
notices, notice_receipts
audit_logs
```

**安全底线（写进技术方案，即使演示未实现也要承诺）：**

- API Key **只存哈希**，明文仅创建时展示一次  
- 管理接口与推理接口权限分离  
- 购额 / 调账 / 改路由 / 撤 Key 全量审计  

### 3.4 算力调度技术要求（替代「算力商品」）

状态机：

```
queued → running → succeeded
                → failed → (retry) queued
queued/running → cancelled
```

Phase 1 可接受：**运维人工推进状态**（模拟 Worker）。  
Phase 1.1 再补：`lease / heartbeat / complete` 内部协议。

计费：预扣 → 成功实扣 / 失败释放；与 API 消耗共用 `token_ledger`。

### 3.5 分期建议（替换「8 周上线大而全」话术）

| 阶段 | 范围 | 验收焦点 |
|------|------|----------|
| **P0 / 8 周 MVP** | 账号机构、项目任务、全联盟需求+应征成交、工作台、官方钱包、Chat 兼容网关、算力作业最小队列、通知已读、撮合订单最小闭环 | 可重复脚本验收，非页面数量 |
| **P1** | 履约担保规则细化、搜索筛选、秘书撮合台、用量审计、Key 哈希、失败退款 | 安全与计费正确 |
| **P2** | 多模型自动路由、图像/视频、多池调度、子 Key、多区域、等保测评准备 | 规模与合规 |

KPI 建议改为可工程验证：例如「需求成交闭环可跑通」「余额不足拒绝调用」「作业失败退款入账」——而不是先写「撮合成功率 70%」。

### 3.6 演示工程修改（可用版）

短期（仍可前端原型）：

1. 页脚固定文案：**「数据仅存本机 localStorage，非生产系统」**  
2. 增加「机构钱包 / 试调用」页（mock 亦可，但要有余额变化）  
3. 去掉或改名 Token 转售相关入口  
4. 导航按 §2.1 重排，出海工作台降为二级  

中期（与真实后端对齐）：

1. 对接服务端 API（至少健康检查 + 登录 + 需求列表 + 钱包）  
2. 演示账号分角色：机构管理员 / 执行人 / 秘书处 / 运维  
3. 提供 `reset demo`（需鉴权），避免公网误伤

## 6. 验收用例（建议你们写进方案，与我方对齐）

1. 机构 A 发布需求后，机构 B 在全联盟广场可见并可应征、确认成交并生成订单。  
2. 项目任务逾期出现在工作台。  
3. 官方购买额度后，用统一 API Key 调用网关，余额下降，流水可查；不足时明确失败。  
4. 提交算力作业 → 入队 → 运行 → 成功，项目或通知可见完成；失败则退款或可解释的冻结释放。  
5. 系统中不存在转售/挂单/机构间余额转让入口。  
6. 秘书处发通知，会员未读→已读可追踪。  
7. 对外材料不声称「等保/多区域已上线」，除非附测评/部署证据。

## 7. 结语

请把本意见视为 **产品主轴纠偏 + 技术诚实性补强**，不是否定撮合交易能力。  
你们的品类大厅、订单与供应商市场，应作为会员中枢上的 **履约与供给网络** 保留并做强；同时用 **官方钱包网关 + 算力调度** 替换 Token 转售叙事，用 **已交付/目标架构分栏** 替换超售口径。

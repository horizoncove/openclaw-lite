## 0. 方法：什么叫「第一性原理」在这里

不做竞品功能对照，先问四层问题：

1. **对象是什么？** 会员机构在联盟里交换的最小价值单元是什么？  
2. **约束是什么？** 哪些物理/经济/组织约束不会因为换一个 App 而消失？  
3. **痛从哪来？** 表面抱怨对应哪条约束被放大？  
4. **软件该碰哪一层？** 信息、协调、信任、产能——各能消除多少摩擦？

结论先说：

> 微短剧联盟会员的核心痛，不是「缺少一个出海官网」，而是在**强协作、强期限、多主体、弱合同数字化**的生产网络里，  
> **状态不可见、承诺不可执行、产能入口碎片化** 三者叠加。  
> 中枢要解的是这三件事；其余模块若不能服务这三件事，就是噪音。

## 1. 行业里不可再分的「原子」

把业务拆到不能再拆：

| 原子 | 定义 | 谁拥有 |
|------|------|--------|
| **作品/项目** | 一部剧从筹备到发行的责任容器 | 需求方机构 |
| **任务** | 项目内可完成的工作切片（有截止） | 执行人 |
| **能力** | 译制/配音/发行/算力等可交付技能 | 供给方机构或平台 |
| **承诺** | 「谁在何时以何条件交付什么」 | 甲乙双方（+ 秘书处担保时） |
| **额度** | 调用模型/算力的预付权利 | 机构（官方发放） |
| **注意** | 需要被知道的事实（逾期、成交、扣费、公告） | 接收者 |

用户一切操作，本质是在这六个原子上：**创建、看见、承诺、履约、计量、通知。**

任何「页面」若不改变这六个原子的状态，对用户没有真实价值。

## 2. 四类摩擦（痛的物理来源）

协作网络里的成本，只能来自四类摩擦：

```
信息摩擦  →  不知道真状态（进度、谁有空、余额、规则）
协调摩擦  →  找人、对齐、确认、催办的往返次数
信任摩擦  →  怕对方不做、怕被白用、怕乱扣费、怕口头协议
产能摩擦  →  实际干活的工具/算力/专业团队获取成本高、入口散
```

### 2.1 信息摩擦（最高频）

**第一性：** 决策需要状态；状态若不在「共享、可信、及时」的载体上，就只能靠问人。

| 表象 | 根因 |
|------|------|
| 「这部戏进行到哪了？」 | 任务状态不在统一对象上，存在于聊天与表格 |
| 「谁应征了我的需求？」 | 意向没有结构化记录 |
| 「这调用扣了吗？」 | 计量与动作不同步或不透明 |
| 「群公告我看了没？」 | 注意没有已读状态 |

**可软件化程度：高。** 工作台、需求状态、流水、已读 —— 本质都是降低信息摩擦。

### 2.2 协调摩擦（最高成本）

**第一性：** 多主体协作的成本 ∝（参与人数 × 不确定次数 × 通道混乱度）。  
微信群把「广播」做得很强，把「定向确认与闭环」做得很弱。

| 表象 | 根因 |
|------|------|
| 群里喊译者 | 供给发现无结构化市场，只能广播 |
| 谈妥后仍反复确认 | 缺少「确认」这一不可抵赖动作 |
| 应征石沉大海 | 供给方无法跟踪承诺链 |
| 秘书处反复拉群 | 撮合过程没有对象化 |

**可软件化程度：中高。** 广场+应征+确认+订单，是在把协调从「会话」升级为「状态机」。

### 2.3 信任摩擦（最高风险）

**第一性：** 交换要发生，必须降低「对方不履行」与「规则被滥用」的预期损失。

| 表象 | 根因 |
|------|------|
| 不敢先干活 | 无订单节点/无托管叙事 |
| 怕乱扣费 | 计费与成败未绑定 |
| 想倒卖额度 | 若系统允许，套利会破坏官方计量秩序 |
| 口头协议扯皮 | 承诺未对象化 |

**可软件化程度：中。** 系统能提供**可验证的痕迹与约束**（订单、流水、禁转售），不能替代法律与人品；但能把「可抵赖」变成「难抵赖」。

### 2.4 产能摩擦（工具层）

**第一性：** 译制/配音/转码等是产能；产能若分散在多个供应商控制台，机构的边际协调成本上升。

| 表象 | 根因 |
|------|------|
| 多家 Key、多家账单 | 采购与计量单元不统一 |
| 长任务靠催 | 异步作业无队列可见性 |
| 出海服务另起炉灶 | 专业产能与日常经营系统断裂 |

**可软件化程度：中。** 统一网关+钱包+作业队列降低「获取与计量」成本；真正GPU与译者产能仍受物理/人力约束。

## 3. 五个核心痛点：从表象挖到根

### 痛点 P1 · 「我不知道现在该盯什么」

| 层 | 内容 |
|----|------|
| 表象 | 群消息刷屏；负责人靠问；执行人靠被催 |
| 五问 | 为什么不知道？→ 状态分散。为什么分散？→ 没有强制写入统一对象的工作习惯与工具。为什么没有？→ 过去用聊天就「够用」。为什么现在不够？→ 并行项目↑、跨机构协作↑、期限更紧。根约束是什么？→ **注意力稀缺 + 状态未结构化** |
| 第一性结论 | 痛的本质是**注意力分配失败**，不是缺少报表图表 |
| 解法边界 | 必须给「逾期/待确认/未读/失败作业」等**可行动信号**；堆 KPI 大屏不解 P1 |
| 对应需求 | J1、U-01 |

### 痛点 P2 · 「跨机构找人又贵又不可靠」

| 层 | 内容 |
|----|------|
| 表象 | 群里喊、熟人介绍、应征无回音 |
| 五问 | 为什么贵？→ 每次都要重新广播与筛选。为什么不可靠？→ 意向与承诺未固化。为什么未固化？→ 聊天是易失介质。根约束？→ **供需匹配需要可检索的供给表达 + 可执行的承诺动作** |
| 第一性结论 | 这是**市场双边匹配**问题，不是「多做几个服务介绍页」 |
| 解法边界 | 全联盟可见需求 + 应征 + 确认 + **订单** 是最小闭环；没有订单的匹配只完成了「认识」，没完成「交换」 |
| 对应需求 | J3–J5、U-03–U-07 |
| 错误解法 | 把匹配做成 Token 挂单市场 → 引入信任负外部性（P3） |

### 痛点 P3 · 「钱与规则说不清」

拆成两个子痛，根因不同：

#### P3a · 合作结算说不清

- 根约束：跨机构交换需要**结算对象**；微信转账≠业务单据。  
- 解法：撮合订单节点（托管/放款/争议）+ 人话规则「这不是饭卡互转」。  

#### P3b · 工具扣费说不清

- 根约束：预付产能权利（Tokens）必须与**调用成败**一致，否则理性用户会少用或不用。  
- 解法：流水可追溯；失败不扣/退回；余额不足显式失败。  

#### P3c · 规则被套利

- 根约束：若额度可机构间转让，系统会从「生产资料」异化为「投机品」，计量与联盟治理失效。  
- 解法：**硬禁止转售**（产品禁区，不是文案偏好）。  

**第一性结论：** 「钱的痛」不是用户要加密货币，而是要**两种完全不同的交换**被正确建模——  
**服务交换（订单）** vs **产能权利（Tokens）**。混为一谈会同时毁掉匹配市场与工具计量。

### 痛点 P4 · 「干活的工具太散、长任务黑箱」

| 层 | 内容 |
|----|------|
| 表象 | 多控制台；转码/批译不知何时好；失败哑巴亏 |
| 根约束 | 同步推理与异步作业是两种产能形态；都需要统一的**身份、配额、状态、账单** |
| 第一性结论 | 用户买的不是「模型品牌页」，而是**可预期的产能获取** |
| 解法边界 | 统一 Key + 目录价 + 试调；作业状态机 + 预扣/释放；不需要先做多区域算力故事 |
| 对应需求 | J6–J8、U-08–U-12 |

### 痛点 P5 · 「专业服务与日常经营两张皮」

| 层 | 内容 |
|----|------|
| 表象 | 出海另有网站/微信对接；进度靠追问 |
| 根约束 | 专业服务是低频高复杂度产能；日常中枢是高频经营系统。二者应**挂钩**而非**互换** |
| 第一性结论 | 用户要的是「办事入口 + 进度回写」，不是「再迁移一次主系统」 |
| 解法边界 | 服务进件/工单挂项目；营销页可独立，但不得自称唯一 SaaS 抢走中枢心智 |
| 对应需求 | J9、U-15 |
| 错误解法 | 用出海宣传站替代会员中枢（历史上反复偏航的根） |

## 4. 痛点优先级矩阵（为何有的必须先解）

评分维度（1–5）：发生频率 · 单次损失 · 是否阻塞主交换 · 软件可解度  

| 痛点 | 频率 | 损失 | 阻塞交换 | 可解度 | 综合 | MVP 态度 |
|------|------|------|----------|--------|------|----------|
| P1 状态不可见 | 5 | 3 | 4 | 5 | **高** | 必须 |
| P2 匹配难闭环 | 4 | 5 | 5 | 4 | **最高** | 必须到订单 |
| P3 钱与规则 | 3 | 5 | 5 | 4 | **最高** | 必须分账+禁转售+计费正确 |
| P4 产能入口散 | 4 | 3 | 3 | 4 | **高** | 必须最小网关+作业 |
| P5 服务两张皮 | 2 | 3 | 2 | 3 | 中 | P1 挂钩即可 |
| 热度/上链焦虑 | 1 | 1 | 1 | 2 | 低 | 不进 MVP |

**推导：**  
没有 P2+P3，联盟只是聊天群的皮肤。  
没有 P1，系统有功能但不会成为每日入口。  
没有 P4，中枢缺少「用了就离不开」的产能抓手。  
P5 重要但不定义品类。

## 5. 从痛点反推的「不可妥协命题」

这些命题若被违背，产品在第一性上失败：

1. **状态必须有主场** —— 逾期、应征、订单、作业、扣费，至少有一处权威状态。  
2. **匹配必须闭到承诺** —— 停止在「浏览卡片」；确认必留痕并生成订单。  
3. **两种钱不可混** —— Tokens≠订单结算；禁止机构间额度转让。  
4. **计量必须与成败一致** —— 失败不应成为静默损失。  
5. **中枢是日常操作系统** —— 出海等是插件式专业产能，不得夺取主场。  
6. **演示≠解除约束** —— localStorage 演示不能假装已消除信任与计量约束。

## 6. 软件解不了什么（避免过度承诺）

| 约束 | 为什么解不了 | 产品应如何诚实 |
|------|--------------|----------------|
| 优质译者稀缺 | 供给侧物理有限 | 匹配提效率，不承诺「一定有人」 |
| 平台流量与分成规则 | 在发行平台侧 | 不做假热度当真数据 |
| 合同法律效力 | 需法务与管辖 | 订单是业务留痕，不是自动胜诉 |
| 算力物理容量 | GPU/队列真实上限 | 显示排队，不吹多区域已具备 |
| 组织执行力 | 人不用系统 | 降低录入成本，不能靠功能堆砌 |

## 7. 对需求文档的修正含义

相对只列 Jobs/故事，本分析要求：

| 若只做… | 第一性评价 |
|----------|------------|
| 很炫的出海落地页 | 几乎不碰 P1–P4 |
| 供需卡片墙但无订单 | 只降了一半协调摩擦，信任摩擦仍在 |
| Token 市场 | 放大 P3c，破坏计量 |
| 网关但计费糊涂 | 用户会理性弃用 P4 |
| 中枢+订单+清晰 Tokens+作业状态 | 对准最高优先级痛点组合 |

因此验收应优先问：

> **P1–P4 是否在真实用户路径上被减轻？**  
> 而不是模块是否齐全。

## 8. 一页推导图（给评审）

```
原子: 项目/任务/能力/承诺/额度/注意
        │
        ▼
四摩擦: 信息 | 协调 | 信任 | 产能
        │
        ▼
五痛点: P1可见性 → P2匹配闭环 → P3钱与规则 → P4产能入口 → P5服务挂钩
        │
        ▼
产品命题: 工作台信号 / 需求→订单 / Tokens与结算分账 / 网关+作业可预期 / 出海为挂接
        │
        ▼
禁区: 转售、主场被营销站替换、失败静默扣费、伪合规话术
```

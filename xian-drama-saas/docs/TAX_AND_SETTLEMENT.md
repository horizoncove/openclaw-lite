# Token 支付链路 · 税务与发票处理（业务方案）

> 版本：**TAX-1.0**  
> 日期：2026-07-25  
> 状态：**产品/商务建议方案（须法务与财务确认后定稿）**  
> 适用：[MVP.md](./MVP.md) 悬赏托管 · [DECISION_TOKEN_SETTLEMENT.md](./DECISION_TOKEN_SETTLEMENT.md) D1.3  
> **本文不是法律意见**；上线前需税务师/律师按主体资质出具意见。

---

## 0. 结论先说

> **Token 本身不作为「纳税对象」。**  
> 税务跟的是 **法币（¥）合同与发票**，以及「谁向谁提供了应税服务」。  
>  
> **推荐商务结构（总包/转包，又称「平台成甲方」）：**  
> 1. 客户向**平台公司**买服务（预付购 T = 预收服务款/预付积分）→ **平台给客户开票**  
> 2. 平台向**供应商**采购履约服务 → **供应商给平台开票** → 平台再向供应商付 T 或兑付 ¥  
>  
> 这样：客户能报销、供应商有收入凭证、平台收入与成本匹配，避免「积分私下划转却无人开票」。

---

## 1. 为什么不能「只转 Token、不问票」

| 若只做站内 T 划转 | 问题 |
|-------------------|------|
| 客户付了 ¥ 却拿不到合规发票 | 企业客户不愿购额 |
| 供应商收到 T（或兑 ¥）无成本/收入票据 | 账务与所得税不清 |
| 平台既经手资金又说「只是撮合」 | 易被质疑资金与税务身份 |

故：**站内 Token = 结算与计量凭证；站外法币发票 = 税务闭环。**

---

## 2. 推荐模式：平台成合同主体（总包 → 外采）

### 2.1 法律关系（建议）

```
客户 ──服务合同/购额协议──► 平台运营公司
平台 ──采购/外包合同──────► 供应商公司
```

- 客户认为：我向平台买「译制/悬赏履约服务」（用 T 计量额度）  
- 供应商认为：我向平台提供外包服务，平台付我 T（后续可兑 ¥）或直接付 ¥  
- **客户与供应商之间不直接签结算合同**（可有保密/交付配合协议，但不走价款）

### 2.2 与 MVP 资金流对齐

```
① 客户 ¥ → 平台（购 T）        【税务事件 A：平台确认预收/收入时点】
②～⑧ 站内：发悬赏→接单→托管 T→验收→平台付 T 给供应商  【一般不单独产生发票，但产生结算单】
⑨ 供应商 T →（后期）官方回收 ¥  【税务事件 B：平台付服务款；供应商确认收入并开票给平台】
   或 MVP 暂不兑 ¥ 时：供应商持有 T，收入确认时点由财务政策约定（见 §4）
```

### 2.3 发票方向（标准）

| 步骤 | 付款 | 发票 |
|------|------|------|
| 客户购 T / 付服务预付款 | 客户 ¥ → 平台 | **平台 → 客户** 开增值税发票 |
| 供应商完成履约、平台结算 | 平台付 T 或 ¥ → 供应商 | **供应商 → 平台** 开增值税发票 |
| 平台撮合费/服务费差价 | 留在平台 | 含在「平台 → 客户」那张票的收入里，或单独服务费票（由财务定税目） |

客户**不向供应商索票**；供应商**不向客户开票**——避免三角票与重复征税扯皮。

---

## 3. 备选模式：纯居间（慎用）

平台只收佣金，价款由客户直付供应商。

| 优点 | 缺点 |
|------|------|
| 平台收入小、票少 | 与「客户 Token 付给平台再付给供应商」的产品流**冲突** |
| | 客户仍要向供应商要票；Token 托管难解释 |

**若产品坚持「钱经平台托管」，不要用纯居间讲税务**，否则资金流与发票流不一致，风险更大。

## 4. 计税时点（需财务定政策）

### 4.1 客户购 Token（¥ → T）

常见两种会计/税务口径（二选一，写进财务制度）：

| 口径 | 做法 | 适用 |
|------|------|------|
| **预收款** | 购 T 时挂预收；任务验收/消耗时再确认收入、开票或红字调整 | 更贴近「先充值后履约」 |
| **销售积分即确认** | 购 T 时即确认收入并开票；未消耗作负债或递延（细则问会计师） | 财务简单，退款复杂 |

**产品侧要求：** 购额单必须有 `org、金额¥、T数量、订单号、时间`；支持按购额单开票申请。

### 4.2 托管与站内付 T（客户 → 平台池 → 供应商）

- **一般不开发票**（无新的法币收付）。  
- 必须生成 **结算单 / 对账单**：任务、T 数量、参考 ¥（`T × P_buy` 或合同单价）、甲乙平台三方。  
- 结算单是后续供应商向平台开票、平台付 ¥ 的依据。

### 4.3 供应商收到 T

| 阶段 | 建议 |
|------|------|
| **仅持有 T、未兑 ¥** | 不强制视同收现金；但合同应约定「T 对应平台应付服务费债权」；财务报表口径问会计师 |
| **官方回收 T→¥** | **强税务事件**：平台向供应商支付劳务/外包款；**先验票（供应商→平台）再打款**（或小额先款后票的例外政策） |
| **供应商把 T 花在平台产能** | 视同用服务费债权抵平台 Usage，减少兑出；开票仍按实际 ¥ 结算净额处理（财务定） |

### 4.4 平台撮合费 / 加价

平台利润来自：购额加价、未兑沉淀、撮合费、C 环合同等。  
收入确认与销项税跟「对客户开票口径」走；成本跟「供应商进项票」走。

## 5. MVP 阶段最小合规做法（可执行）

MVP 若**暂不开放回收兑 ¥**：

1. **购 T：** 平台与客户签《预付服务/积分协议》；按财务口径给客户开票（预收或销售收入）。  
2. **悬赏履约：** 平台与供应商签《外包服务框架》；站内验收后出 **电子结算单**（任务、T、参考¥）。  
3. **付 T 给供应商：** 记平台对供应商的 **应付积分/应付服务费**；发票可约定「兑 ¥ 或月结时一并开具」。  
4. **系统必留：** 购额流水、托管流水、放款流水、结算单 PDF/编号——供财务对账。  
5. **主体：** 仅企业会员；对公账户；禁止个人卡提现叙事。

MVP 一旦开放 **R 回收**：

```
供应商申请兑 ¥
  → 上传/关联：供应商向平台开具的发票（金额≈兑付¥）
  → 财务审核票面与结算单一致
  → 平台对公打款
```

**无票不兑**（或仅战略白名单例外）——写进产品规则。

## 8. 待法务/财务拍板清单

1. 运营主体营业执照范围是否覆盖「信息技术/制作服务/外包」  
2. 购 T 开票税目与税率（现代服务？还是其他）  
3. 预收 vs 即时确认收入  
4. 供应商无票时能否兑付、限额多少  
5. 跨境供应商（若有）另案（代扣代缴等）  
6. 联盟秘书处与平台公司是否同一纳税主体

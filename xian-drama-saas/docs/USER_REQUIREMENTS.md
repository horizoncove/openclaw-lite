## 1. 我们为谁解决问题

西安微短剧产业联盟的会员，主要是**机构**（制片公司、译制/配音团队、发行相关方），不是 C 端观众。

他们每天真正操心的不是「有没有一个很炫的出海官网」，而是：

1. **我的戏/项目进展到哪了，谁卡住了**  
2. **缺译者/配音/发行合作时，怎么在联盟里快速找到人对接，并留痕成交**  
3. **译制、字幕、配音、转码这类 AI/算力活，能不能一个入口做完、费用清楚**  
4. **联盟通知、分账/托管、出海服务进度，别再靠群消息刷屏**

一句话用户价值：

> **让会员机构在一个中枢里，把「项目进度、找人对接、AI/算力用量、关键通知」办完；出海专业服务按需申请，而不是另学一套系统。**

## 2. 用户画像（谁在点屏幕）

### 2.1 王敏型 · 机构负责人 / 管理员

| 项 | 内容 |
|----|------|
| 代表诉求 | 对结果负责：预算、进度、对外合作、别出事 |
| 典型一周 | 盯几部戏的节点；批一笔合作；给团队开通工具额度；看联盟通知 |
| 成功标准 | 打开系统 1 分钟知道「今天要处理什么」；钱和合作有据可查 |
| 痛点 | Excel/群聊碎片化；找合作靠人脉；各家 AI 控制台各充各的 Key |
| 不关心 | 底层有几层架构、等保口号、区块链话术 |

### 2.2 执行人型 · 制片 / 译制 / 协调

| 项 | 内容 |
|----|------|
| 代表诉求 | 把任务做完：字幕、配音、对接译者、催进度 |
| 典型一天 | 看自己的待办与逾期；在联盟里应征或发布具体需求；跑翻译/试调用 |
| 成功标准 | 待办清晰；应征有回音；工具调用失败能懂「为什么」（余额不足/作业失败） |
| 痛点 | 截止日靠人催；应征后石沉大海；调用失败不知是否扣费 |

### 2.3 供给方型 · 译者 / 配音 / 小型承制（同为会员机构）

| 项 | 内容 |
|----|------|
| 代表诉求 | 接到活、谈清楚、做完能结算 |
| 成功标准 | 能浏览联盟需求；应征后能跟踪状态；成交后有订单节点可查 |
| 痛点 | 群里抢单无规则；谈妥了没有正式单据；钱怎么结说不清 |

### 2.4 陈希型 · 联盟秘书处

| 项 | 内容 |
|----|------|
| 代表诉求 | 撮合、公告、争议协调、会员服务秩序 |
| 成功标准 | 通知能送达并知悉已读；争议订单有处理入口；规则（禁转售等）被系统守住 |
| 痛点 | 通知靠群；争议靠私聊；规则靠口头 |

### 2.5 韩磊型 · 服务中心 / 运维专员

| 项 | 内容 |
|----|------|
| 代表诉求 | 推进出海服务单、推进算力作业队列 |
| 成功标准 | 工单/作业状态可改、会员侧能看见结果 |
| 痛点 | 会员反复问进度；失败任务费用说不清 |

### 2.6 非目标用户（本期不服务）

- 普通观众（看剧、充硬币）  
- 想做 Token 倒卖/挂单套利的人  
- 需要「司法级存证已上线」承诺的法务场景（可展望，非当前使用需求）

| ID | 用户要完成的事 | 今日替代方案 | 期望体验 |

| J10 | 收到并确认联盟重要通知 | 群公告 | 列表+已读；能点进相关业务 |

## 4. 关键使用场景（叙事）

### 场景 A · 周一早上：负责人打开中枢

王敏登录后进入工作台，希望立刻看到：

- 有没有**逾期任务**（红）  
- 有没有人应征了我发的需求、**待我确认**  
- 钱包 Tokens 是否快不够  
- 有没有未读联盟通知  

**用户语言验收：** 「不用问制作人，我自己知道今天先点哪里。」

### 场景 B · 缺阿拉伯语字幕：发布需求 → 成交

1. 王敏在「工作需求」发布：品类=翻译，说明集数/期限/预算，一键发布（全联盟可见）。  
2. 丝路侧马川在广场看到，点应征并留言。  
3. 王敏在「我发布的」里看到应征列表，确认一位。  
4. 系统生成**撮合订单**；双方都能在「撮合订单」里看到托管/进行中等节点。  
5. 马川在「我应征的」里看到已成交。

**用户语言验收：** 「群里不用再截图证明谈妥了；订单上写得清。」

### 场景 C · 译制执行：调用模型 + 跑批作业

1. 执行人打开「模型网关」，用机构 Key 试调一段翻译，看到余额减少、流水多一条。  
2. 余额不够时，调用失败提示「余额不足」，且**没有悄悄扣费**。  
3. 提交「字幕批处理」算力作业，看见排队→运行→成功；成功后工作台/通知有提醒。  
4. 若失败或取消，预扣费用退回，流水能解释。

**用户语言验收：** 「工具费用像话费账单一样能看懂；失败不会闷声扣钱。」

### 场景 D · 想做出海但不想另学系统

1. 王敏从项目点「申请出海服务」或打开服务介绍页进件。  
2. 服务中心接单后，她在中枢工作台看到工单进度（评估中/履约中…）。  
3. 她仍在中枢管项目与需求，不被迫迁到另一套「出海 SaaS」当主系统。

**用户语言验收：** 「出海是找专业团队办事，不是让我换一个家。」

### 场景 E · 秘书处发通知

陈希发布通知 → 会员未读 → 点开已读；重要通知可跳到需求或订单。  
**用户语言验收：** 「别再问我看没看群。」

### 场景 F · 有人想倒卖额度（反场景）

任何角色都**找不到**「挂单卖 Tokens / 转给其他机构」的入口。  
**用户语言验收：** 「系统不支持倒额度，省得扯皮。」

## 5. 用户路径需求（按界面感知）

以下按「用户以为自己在用的页面」描述需求，不绑定实现技术。

### 5.1 登录与身份

- 用联盟账号进入「会员中枢」  
- 能区分：我是哪家机构、什么角色  
- 演示/培训需要：**切换不同机构角色**走完发布-应征，否则无法理解闭环  

### 5.2 工作台（每日首页）

用户要看到的信号（优先级从高到低）：

1. 我的逾期 / 阻塞任务  
2. 待我确认的应征  
3. 未读通知  
4. 进行中的算力作业  
5. Tokens 余额是否健康  
6. （次要）发行分账等提醒  

不需要一进门就是热度榜、区块链证书墙。

### 5.3 我的项目

- 建项目、改阶段、看任务列表  
- 任务可标完成/阻塞/截止日期  
- 能从项目跳到关联的需求、订单、作业（有则显示）  

### 5.4 工作需求

三个用户心智抽屉：

| 抽屉 | 用户问题 |
|------|----------|
| 全联盟广场 | 「外面有什么活/需求？」 |
| 我发布的 | 「我发的进展如何？谁应征了？」 |
| 我应征的 | 「我投的哪些有回音？」 |

发布时用户要填：要什么、能提供什么、品类、预算/条件、期限。  
发布后默认**全联盟可见**；用户不需要理解「可见性配置」，只要知道「关掉=下架」。

### 5.5 撮合订单

用户心智：「这是合同进度单，不是充值余额。」

要能看见：对应哪条需求、甲乙是谁、金额怎么写的、现在到哪一节点（托管/进行中/已放款/争议）。  
要能读懂一句人话：**订单结算不是把我的工具额度转给对方。**

### 5.6 机构钱包（工具额度）

用户心智：「这是机构公用的 AI/算力饭卡。」

- 官方买额度（付钱 → 到账 Tokens）  
- 看余额、本月花了多少、流水  
- **不能**卖给别的机构、不能挂单  

### 5.7 模型网关

用户心智：「一个入口调模型，账单在钱包。」

- 看有哪些模型、大概怎么计费  
- 复制/轮换 Key（明白密钥很重要）  
- 试调用后立刻感到余额变化  
- 没钱时明确失败原因  

### 5.8 算力作业

用户心智：「丢进队列的长任务。」

- 提交时知道大概预扣多少  
- 看状态：排队/运行/成功/失败/取消  
- 失败或取消：钱回来  
- 成功：有通知或回项目  

### 5.9 消息中心

- 列表、已读/未读  
- 能点进相关业务（需求/订单/作业/钱包）  

### 5.10 出海专业服务（次入口）

- 了解服务、提交进件  
- 在中枢看工单进度  
- 不要求用户把「出海站」当成日常首页  

### 5.11 用户明确不需要出现在主路径的东西

- Token 市场 / 转售  
- 一打开就「版权链司法采信 100%」  
- 未说明的「真实八大平台热度」当主功能  
- 让用户在三个都叫 SaaS 的网站之间迷路

## 7. 用户可感知的规则（必须写成产品语言）

1. **需求发出去，盟友默认都能看见**（不是私密小圈子招标，除非还是草稿）。  
2. **工具额度（Tokens）只能官方买、自己花**，不能卖给其他机构。  
3. **合作订单的钱**和 **工具额度** 是两件事：订单托管/放款不是「把饭卡余额转给对方」。  
4. **调用失败 / 作业失败**，用户应能在流水里看到合理解释（不扣或退回）。  
5. **出海服务**是「找联盟专业团队办事」，日常首页仍是会员中枢。

## 8. 用户成功指标（产品是否好用）

不追求空洞的「上线页数」，用用户行为定义成功：

| 指标 | 用户含义 | MVP 观察方式 |
|------|----------|--------------|
| 工作台回访 | 是否当成每日入口 | 登录后首屏停留/回访 |
| 需求成交闭环 | 是否真能找到人对接 | 发布→应征→确认→订单 完成率 |
| 计费可读 | 是否敢用网关/算力 | 试调与作业后查看流水的比例；客诉「乱扣费」次数 |
| 通知触达 | 是否替代部分群公告 | 已读率 |
| 迷路率 | 是否被多入口搞晕 | 用户是否问「到底用哪个网站」 |

## 9. 与旧方案表述的对照（避免再偏航）

| 用户真正要的 | 容易做错的交付 |
|--------------|----------------|
| 每天能办公的中枢 | 只做出海宣传落地页 |
| 找人对接并留痕 | 只做供需卡片墙，没有订单 |
| 一个饭卡用 AI/算力 | Token 市场、转售、多 Key 丛林 |
| 失败可解释 | 先扣费再调模型、失败不退 |
| 出海可申请 | 再做一个「第二官网」逼用户搬家 |
| 规则清晰 | 等保/多区域/上链当已上线能力卖 |

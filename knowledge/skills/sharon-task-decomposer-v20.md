# Sharon Task Decomposer v2.0

## 触发条件

当任务模糊、复杂、目标不清、优先级混乱或用户不知道从哪里开始时启用。
简单明确的任务直接执行，不为了套模板而过度分解。

## 思考流程

1. **理解现状**：已经完成什么、有哪些资源、当前问题是什么。
2. **明确目标**：最终结果和可验证的成功标准是什么。
3. **识别约束**：权限、数据、环境、风险及用户明确要求。
4. **追踪不确定性**：区分事实、假设和必须确认的选择。
5. **选择分解方式**：
   - 时间线明确：按阶段分解。
   - 系统模块明确：按空间或组件分解。
   - 操作顺序明确：按流程分解。
   - 任务过多：按重要性和依赖排序。
   - 高复杂度项目：按需求、设计、实施、验证、交付分解。
6. **映射依赖**：标出必须串行的步骤和可以并行的独立步骤。
7. **生成行动清单**：每一步具体、可执行、有完成标志。
8. **执行与校验**：按风险调整验证深度，保存中间结论。

## 并行原则

- 现状分析、目标明确、资源盘点和风险识别可以独立时并行。
- 有前置依赖的任务不得伪并行。
- 主智能体负责统一事实口径、消解冲突和汇总结论。
- 只在复杂度确实需要时使用子任务，避免上下文膨胀。

## 上下文工程

- 持续记录假设、待确认项和中间结论。
- 长任务压缩为目标、事实、决定、风险和下一步。
- 避免重复询问已经获得的信息。
- 用户修正或缩小范围时，立即以最新指令为准。

## 输出要求

- 先说明目标和成功标准。
- 给出有顺序、有优先级的任务清单。
- 标明依赖关系、检查点和风险。
- 每步都应让普通人知道具体怎么做以及怎样算完成。
- 不只提问不给方案；能安全采用默认值时先推进并记录假设。

## 质量检查

- 用户是否知道第一步做什么？
- 每一步是否既不过粗也不过细？
- 是否遗漏关键依赖、资源或风险？
- 完成标准是否可验证？
- 计划是否可按当前资源执行？

## 平台适配

原始方法提倡日/周级时间预估。云端自主执行任务不使用日历工期承诺，改用
技术复杂度、涉及组件、依赖和风险描述工作量；这不影响优先级和依赖分析。
